# Phase 5.2.3 — synchronized Windows and GPU diagnostics

12 November 2026, Asia/Calcutta. **Diagnostics only. No stabilization or AC-performance acceptance claim.**

## Conditions and permissions

Windows GetSystemPowerStatus and two battery interfaces reported discharge despite the physically connected charger. The user explicitly authorized **battery-condition diagnostics with limits documented**. No power plan, Battery Saver, driver, pagefile, cache or application setting was changed. AC=0 and Battery Saver=0 are validated at endpoints and once per telemetry sample. Per-run battery ranges are in the JSON; a changing battery percentage is a performance-comparison limitation. Actual NVIDIA GTX 1650 rendering and 1920×1080 WebGL buffers are checked per run. Quality and production code were preserved. No user browser profile/save was opened or reset.

The authorized hidden administrator helper records built-in WPR GPU.Light windows, stops only its own successfully started recording and enforces a 150-second safety timeout. Local browser/CIM/counter access required execution outside the restricted sandbox. No additional tool installation or system setting change was needed. WPR/PDH/browser recording add overhead; the clean controls have neither WPR nor browser tracing. CPU sampling profiler startup is absent in all new runs. Stops/merge work happens after frame capture is disabled.

## Timestamp-correlated significant gaps

The largest synchronized render gap was **497.8 ms**, UTC **19:05:19.343–19:05:19.840** on 11 November (local 12 November **00:35:19.343–00:35:19.840**), renderer PID/TID **21172/14644**. Scheduling reconstruction finds **332.67 ms off CPU**, comprising about **289.50 ms blocked** and **43.17 ms runnable/ready delay**, leaving approximately **165.13 ms on CPU**. No direct renderer-main or GPU-process hard-fault interval overlapped this particular gap. Several wakes are flagged ReadiedFromDPC, but waker IDs decode as -1, so the specific wake owner/wait object remains unknown. This is a mixed execution/wait event, not 498 ms of GPU drawing or AI computation.

Owned Chrome GPU-process packets were traced through Context → Device → process and adapter identities. A context on **AMD vendor 4098/device 5688**, LUID 67112, submitted sequence 4149 at **19:05:19.0932087Z**; matching DMA start was **19:05:19.8614298Z** and stop **19:05:19.8649643Z**. That is **768.22 ms submit-to-DMA-start** and **3.54 ms observed DMA span**, overlapping the combat gap's period. Sparse matched AMD packet delays reach **810.64 ms**. This is **not** a GTX 1650 render-duration measurement or proof that this exact packet blocked the renderer. NVIDIA vendor 4318/device 8093 was separately identified as LUID 72024; its sampled dedicated usage in combat sync1 peaked near **521 MiB**, with **399–1068 MiB** system RAM available across that recording. No sampled 4 GB VRAM exhaustion was observed; transient residency/budget pressure remains unproven. [Packet/context evidence](phase523-synchronized-traces/combat-sync1/gpu-queue-analysis.json).

The 69.1 ms menu gap has **60.39 ms of main-thread hard-fault overlap** and 62.25 ms off CPU; backing filenames are unavailable. This supports paging involvement in that smaller event, with an approximately **18.12 ms conservative cross-clock allowance** limiting exact browser-overlap attribution. It is not automatically a pagefile read or the cause of the historical 521.3 ms event. The mixed-power combat run's 101.5 ms rAF gap similarly overlaps about 60.74 ms of main-thread hard faults.

The unprofiled combat control reached **437.0 ms** in the dedicated render log, showing tracing is not necessary for a battery-condition stall. The instrumented run had many more severe gaps, and WPR emitted millions of driver events, including over 712,000 Profiler/Start callbacks in combat sync1. Recorder writes are visible. The CPU sampling profiler was off, but the overall recording cost is not zero and cannot be removed statistically with this small sample.

The final combat window changed AC state at **19:08:57.1397907Z / 00:38:57.1397907 local**, inside its measured 60 seconds. It is retained but excluded from consistent battery comparisons: **five consistent battery windows, one mixed-power window**. The low maximum in that mixed run is not proof that connecting AC fixed the stalls. Legacy combat harness counters continued during trace delivery; only dedicated frames.json start/end records define the reported 60-second metrics.

## GPU, memory and disk interpretation limits

GPU context queues and hardware queues represent different stages; a nearby GPU event or QueuePacket name alone does not prove a queue delay. Context/sequence pairing and ownership must be valid before assigning a packet to this game's GPU process. Raw packet data is retained even where a numeric queue latency cannot be established. See [Microsoft's context CPU queue explanation](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/context-cpu-queue) and [GPUView collection/analysis scope](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/using-gpuview).

RAM availability, system commit/limit, hard-fault reads, disk throughput/latency and per-adapter dedicated/shared/local usage were sampled at about 1 Hz. Their exact paths, validity statuses and min/max are retained. These samples can miss sub-second peaks; they do not by themselves prove VRAM exhaustion, a pagefile read or the cause of a particular frame. Hard-fault backing filenames and disk timing are used when available. Recorder .etl writes are marked separately. DPC/ISR durations and ReadyThread wakers are evidence of activity, not proof of a faulty driver. Proprietary driver symbols and a complete symbolized wakeup dependency are not established. Parser field semantics follow [Microsoft's kernel parser](https://github.com/microsoft/perfview/blob/main/src/TraceEvent/Parsers/KernelTraceEventParser.cs).
